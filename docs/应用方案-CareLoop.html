01 痛点与场景洞察

医疗照护存在一个结构性的「空窗期」：患者出院后的 2–8 周。

这段过渡期恰恰是风险最高的阶段：手术切口待愈合、用药方案刚调整、身体机能仍在恢复，但院内有护士盯着，长期慢病有多年习惯，唯独这两者之间的窗口期没人管。患者靠自己记医嘱、家属靠微信群问进度、护士靠出院时留的一张纸。

三类真实痛点

角色出院后的真实处境
患者多为 60 岁以上术后老人：医嘱记不全（一天 3 种药 × 多个时段）、症状变化不会判断轻重、不适时不知该忍还是该去医院。
家属白天上班无法陪护，想知道「今天药吃了没」只能打电话问；老人报喜不报忧，异常往往滞后得知。
医护随访护士一人管上百名出院患者，靠「打电话 + 手工记录」；谁漏服、谁体征恶化，完全被动等患者上门，无分级无优先级。

与现有方案的本质区别

医院现有随访系统的形态是「护士打电话 + 手工记录」；市面用药提醒 App 只解决「到点响铃」。两者的共同缺口是：多方协同动作没有变成可流转、可留痕、可追溯的状态。愈见 CareLoop 把「患者漏服了怎么办」这件事，做成患者、家属、护士三方共享的一个状态机——每一步自动流转、跨端实时可见、任一环节打卡即闭环。

场景契合说明：本作品定位与本届赛题「医疗健康」场景分类中的诊后回访监测、患者问答、用药提醒三项逐一对应，是官方参考场景的完整组合落地。

需求优先级的原则

我们刻意把需求收敛在「漏服 → 升级 → 处置」这一条主线上，而不是堆功能：用药提醒、症状自查、AI 问答都只是入口，真正的产品是它们串起来的处置闭环。评委可在作品内验证：患者端任何一个动作，家属端与医护端都会自动同步出现对应状态。

四个差异化主张（均可在作品内当场验证）

主张含义
① 升级链真实可追漏服后 L0→L3 逐级升级（本人 → 家属 → 护士站），任一环节打卡即终止；每一步跨端实时可见，不是前端演示动画，是数据库真实状态流转。
② 分诊规则公开可查红旗规则全文写在患者端「分级规则说明」面板，评委可当场点开；规则只兜底不包办，拿不准时从严。
③ 红色只留给真正的红旗红 = 立即就医，黄 = 电话随访。漏服升级链最高到黄色「需医护回电」——徽章语义回归临床，不做告警疲劳。
④ 对照他自己每个患者的体征基线是他本人近 7 天的滚动中位数 + 偏离带，而非人群正常值；报告与分诊都以「相对他自己的变化」为准。

04 核心机制

机制一：漏服升级链 L0 → L3（服务的状态机，不是提醒闹钟）

L0 · 到点
基础提醒
到达服药时段，患者端收到提醒；同时段多种药合并为一条（列出全部药名）
漏服后
第 1 级 · 提醒本人
每 10 分钟再次提醒患者，可「已服 / 稍后 / 跳过」
30 分钟
第 2 级 · 家属协助
家属端收到协助任务：代打卡 / 已电话联系 / 反馈「仍无响应」
1 小时
第 3 级 · 医护介入
升级至医护预警中心（黄色「需医护回电」），处置后自动回执患者
  • 终止条件：任一阶段完成有效打卡，升级链立即终止——不制造负罪感，全部服完时的空状态文案是「好好休息」。
  • 未绑定家属：跳过第 2 级，满 1 小时直接升级医护端（边界场景已覆盖）。
  • 家属「仍无响应」：转黄色交还医护回电，不升级红色（红色语义只留给分诊红旗与危险体征）。
  • 工程实现：pg_cron 每分钟扫描提醒状态机（每药一行 per-(计划,时段) 粒度），消息写入带 dedup_key 唯一索引幂等，同一事件绝不重复触发。

机制二：症状三级分诊，直通医护预警

红 · 立即就医
红旗规则命中且严重度达标（如剧烈胸痛 ≥5/10）、体温 ≥39℃、收缩压 ≥180mmHg；自动生成医护端红色预警
黄 · 建议联系随访
低严重度命中红旗词 / 中度异常体征；24h 内医护电话评估，同时生成黄色预警
绿 · 居家观察
症状轻微且体征正常；给常规康复指导，不惊扰任何人

规则与 AI 双通道：红旗规则兜底（含口语变体，如「胸口有点闷」），未命中交给大模型结合出院诊断、既往史、当前体征综合分级；AI 不可用时按严重度从严兜底。规则全文对患者公开，分级建议不做确诊承诺。

机制三：家属协同，带来源标注

家属可以代打卡、代填体征，但每一条代操作都带结构化的来源标注（操作人类型 = 家属、操作人姓名），医护端 360 视图有专门的「家属代填记录」卡，时间轴上有弱标签。数据诚信 这在医疗场景里不是锦上添花：家属代填的体征如果与本人自测混在一起，会污染临床判断。

机制四：个人基线 —— 每个患者唯一的对照是他自己

人群正常值对术后老人常常失真（68 岁术后患者的「正常血压」和体检标准不是一回事）。本作品用每个患者近 7 天打卡数据的滚动中位数 + MAD 偏离带作为他的个人基线：

  • 健康打卡页：今日数值对照「他自己的 usual 区间」给出人话反馈（「今天血压比您平时略高，已记录」）
  • 症状分诊：输入体征时同时对照个人基线与通用参考值
  • 样本不足（<3 天）时明确标注「样本不足，暂用通用参考值」——不许装作有基线

辅助机制：履约风险预测与最小打扰提醒

机制作用
CareRisk 履约风险分用近 14 天用药/打卡/症状轨迹计算每位患者的履约风险，帮护士把有限精力投给最可能脱管的人。
自适应提醒节奏对长期依从性好的患者减少打扰频次，对易漏服患者加密提醒——把「提醒」从广播变成个性化。
三条主机制 + 两条辅助机制共用同一套真实数据底座（详见第 06 章），互相咬合：基线喂给分诊、风险分排随访优先级、升级链兜底触达——这是「机制」与「功能清单」的区别。

05 AI 能力全景

四个 AI 模块各管一段，全部围绕「让 2–8 周窗口期的信息流动起来」。

模块输入 → 输出AI 在其中的核心作用
出院小结解析 出院小结拍照 / 上传 → 结构化用药计划草稿，患者确认后生效 多模态识别把纸质医嘱变成可执行数据，错误率远低于老人手抄；AI 只出草稿，人确认才生效，安全边界清晰。
症状三级分诊 主诉（语音/点选/文字）+ 严重度 + 体征 → 红/黄/绿分级 + 人话建议 + 证据 红旗规则兜底 + 大模型综合分级双通道；输出附带命中规则与个人基线对照的证据说明，可解释而非黑箱。
智能问答（RAG） 自然语言提问 → 流式回答 + [依据: 个人医嘱 / 知识库《标题》] 引用标注 双路检索（个人出院资料 + 院内知识库）喂给模型，只基于资料回答；识别高危症状时回答下方出现「一键同步医护端 / 直拨随访电话」动作卡。
随访报告生成 选定周期 → 依从率 / 体征趋势 / 预警处置统计 + 文字总结 把护士每周 2 小时的手工周报压成一次点击，统计口径与数据库一致。

AI 安全设计（医疗场景的生命线）

  • 不编造：资料中无依据时明确说「现有资料无法回答」并建议联系医护；知识库检索不到就如实说，不硬凑。
  • 不越界：不做确诊、不调整用药剂量；涉及病情变化一律建议就医；全站标注「不构成诊断」。
  • 可降级：AI 网关不可用时自动切换本地知识库检索，回答明确标注「本地检索 · 非 AI 回答」——绝不把降级内容伪装成 AI 生成；再退一步还有前端兜底。断网/限流场景下助手不会哑巴。
  • 可审计：分诊规则全文公开在患者端面板；问答带引用来源；家属代填带来源标注。

06 技术方案：秒哒平台承载的生产级架构

全部构建于百度智能云秒哒平台：前端应用与托管后端一体化交付，无本地数据库、无自建服务器。

应用层
React + TypeScript + Tailwind（秒哒源码模板导出后持续迭代），三端一套代码，路由级代码分割
数据层
秒哒托管 Supabase：PostgreSQL 14 张业务表 + RLS 行级安全（患者只能读自己的数据，医护按角色授权）
服务层
8 个 Edge Functions（Deno 运行时）：分诊 / 问答 / 解析 / 报告 / 提醒扫描 / 计划确认 / 注册 / 预警响应

实时层

07 用户体验设计：适老化是硬指标，不是口号

核心用户是 68 岁的老人——所有体验决策围绕「他能不能独立用起来」。

能力落地方式（全部已实现，可当场验收）
看得清三档字号一键切换（根字号全局缩放，持久化），正文对比度 ≥4.5:1
听得懂医嘱与消息一键语音朗读；提示语全部人话（「没有听到声音，请靠近一点再试一次」而非错误码）
说得出症状自查支持语音输入（按住说话，中文识别）+ 8 个常见症状点选标签，主诉可全程免打字
点得准触控目标 ≥44×44px；常用动作置顶、次要项折叠；「沿用上次数值」一键填充
分得清风险三重编码（浅色底 + 图标 + 等级文字），绝不只靠颜色区分；红色只出现在真正紧急处
不被吵同时段多药合并为一条提醒；预警中心按患者聚合（先处理人再处理事）；消息按紧急度排序、未读置顶、降噪折叠

三端形态刻意不同

患者端 / 家属端是手机竖屏体验（桌面访问时渲染设备框，明确移动端定位）；医护端是桌面宽屏工作台（左侧导航 + 数据看板）——跟随真实使用场景，而不是一套界面硬套三个角色。护士在电脑前集中处理，老人和家属在手机上碎片操作。

完整操作：患者完成用药打卡（已服/稍后/跳过）与健康打卡（体征录入对照个人基线）；家属在概览页查看照护对象今日进度并代打卡（医护端可见「家属代填」标注）；医护在 360 详情的照护时间轴里纵览「出院 → 每日 → 异常 → 干预 → 转归」。

09 应用前景与商业模式

谁付费，进哪个科室

要素答案

付费方医院随访外包服务商 / 科室运营预算，按在管患者数订阅（人均月费低、科室总预算友好）
推广路径单科室试点（1 名护士 + 30 名患者即可跑通闭环）→ 院内复制 → 区域随访外包平台。对患者与家属永久免费——守住依从性数据源。
与 HIS 对接后端为标准 Postgres，HIS 侧只需在出院事件发生时 webhook 推送患者基本信息与医嘱、随访结论回写即可；支持私有化部署（医疗数据不出院）。
商业化边界真实短信/推送网关按需接入；演示环境已诚实标注「演示通道」，不冒充生产能力。

为什么这件事发生在现在

  • 政策面：术后加速康复（ERAS）与延续性护理被持续写入护理质控方向，出院随访从「nice to have」变成考核项。
  • 技术面：无代码平台 + 托管后端让「三端 + 状态机 + AI」这种量级的系统可以被学生团队在一个比赛周期内做出生产级完成度——这本身即是本赛题价值的证明。
  • 结构面：老龄化 + 独生子女照护结构，家属远程协同是唯一可规模化的补位方案。

结语

愈见 CareLoop 没有发明任何单一功能——用药提醒、AI 问答、拍照识别都早已存在。我们做的是把它们拧成一条「患者 → 家属 → 护士」三方共享的处置状态机，让出院后最危险的几周第一次有了「不依赖任何人自觉」的照护底座。三个机制、四个 AI 模块、14 张真实流转的数据表——欢迎在作品里逐项验证。

本作品为参赛团队原创，基于百度智能云秒哒平台构建；全部医疗建议均标注「不构成诊断」，演示数据均为虚构脱敏。
